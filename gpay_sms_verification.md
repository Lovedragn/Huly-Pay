Implement the following payment-verification workflow in my existing Huly.Pay project.

IMPORTANT:
- First inspect the existing Flutter project, Android native code, payment services, QR scanner, Spring Boot backend, database entities, APIs, and current payment flow.
- Do NOT rewrite unrelated code.
- Do NOT change the existing UI/design unless required for this workflow.
- Reuse the existing architecture and services wherever possible.
- This is a DEVELOPMENT/TESTING implementation.
- Huly.Pay uses Supabase only for authentication/JWT. Spring Boot remains responsible for business logic, validation, transaction processing, and PostgreSQL access.
- Do NOT use Firebase Authentication or Firebase database.
- Do NOT fake payment success.

==================================================
TARGET WORKFLOW
==================================================

The required flow is:

1. USER SCANS QR IN HULY.PAY
   ↓
2. Flutter extracts the UPI QR content
   ↓
3. Flutter sends the extracted payment information to Spring Boot
   ↓
4. Backend creates/stores a PENDING payment transaction
   ↓
5. Huly.Pay opens Google Pay as a SEPARATE Android application
   ↓
6. Google Pay operates independently from Huly.Pay
   ↓
7. User scans the merchant QR AGAIN inside Google Pay
   ↓
8. User enters the amount in Google Pay
   ↓
9. User completes the payment in Google Pay
   ↓
10. User returns to Huly.Pay OR Huly.Pay remains waiting
   ↓
11. Huly.Pay waits for a NEW incoming transaction SMS
   ↓
12. Android detects the incoming SMS
   ↓
13. Huly.Pay reads the SMS
   ↓
14. Flutter/native Android sends the SMS information to Spring Boot
   ↓
15. Spring Boot verifies the SMS against the pending Huly.Pay transaction
   ↓
16. If matching successful transaction SMS is found:
       mark payment SUCCESS
   ↓
17. If matching failure SMS is found:
       mark payment FAILED
   ↓
18. If no matching SMS arrives within 5 minutes:
       mark payment as FAILED/TIMEOUT

==================================================
PART 1 — QR SCANNING
==================================================

Use the existing QR scanner implementation.

When the user scans a QR in Huly.Pay:

Extract at minimum:

- raw QR content
- UPI ID / pa
- payee name / pn
- amount / am if present
- currency / cu
- transaction reference / tr if present
- merchant code / mc if present
- transaction note / tn if present

Only accept valid UPI payment QR content.

Do not treat arbitrary URLs or text as a UPI payment QR.

If the QR contains no amount, preserve the existing Huly.Pay amount-entry flow.

==================================================
PART 2 — CREATE PENDING TRANSACTION
==================================================

Immediately after the first Huly.Pay QR scan, create a pending payment record through the existing Spring Boot API.

The backend must associate the transaction with the authenticated Supabase user.

Flutter must NOT send a user ID as the authority for ownership.

Use the authenticated JWT:

Authorization: Bearer <SUPABASE_ACCESS_TOKEN>

Spring Boot must extract the authenticated user's identity from the JWT.

Store enough information to identify the payment later, including where supported by the existing schema:

- payment ID
- authenticated user
- merchant UPI ID
- merchant/payee name
- expected amount if known
- currency
- original QR content
- transaction reference generated by Huly.Pay
- status = PENDING
- created timestamp
- payment location if the existing workflow already captures it

Generate a unique Huly.Pay transaction reference for this attempt.

Example:

HULY<timestamp>

Do not reuse transaction references.

==================================================
PART 3 — OPEN GOOGLE PAY AS A SEPARATE APP
==================================================

This is important.

Huly.Pay should NOT try to display Google Pay inside the Flutter application.

The user specifically wants Google Pay to open as a completely separate application.

When the user presses the existing "Open Google Pay" / payment button:

Launch Google Pay as an external Android application.

For THIS workflow, do NOT automatically construct a payment screen inside Google Pay from Huly.Pay.

The user will manually:

1. open Google Pay
2. scan the merchant QR again
3. enter the amount
4. pay

Therefore the immediate Android action should simply launch the Google Pay application.

Use the Google Pay Android package:

com.google.android.apps.nbu.paisa.user

Check whether it is installed.

If it is not installed, show the existing appropriate error/fallback.

Do NOT force a UPI payment intent for this particular workflow.

Do NOT use url_launcher to pretend that payment succeeded.

Launching Google Pay only means:

GOOGLE_PAY_OPENED

It does NOT mean:

SUCCESS
SUBMITTED
PAID

==================================================
PART 5 — LISTEN FOR NEW SMS
==================================================

DO NOT simply wait 5 minutes and then read the entire SMS inbox.

Instead:

After Google Pay is opened / payment verification begins:

Start a 5-minute payment verification window.

During this window, listen for NEW incoming SMS messages.

The desired behavior:

PAYMENT_PENDING
      ↓
START 5 MINUTE TIMER
      ↓
LISTEN FOR NEW SMS
      ↓
SMS ARRIVES
      ↓
CHECK WHETHER IT LOOKS LIKE A TRANSACTION SMS
      ↓
SEND RELEVANT SMS TO BACKEND
      ↓
BACKEND VERIFIES IT

If no matching SMS arrives after 5 minutes:

PENDING
  ↓
TIMEOUT
  ↓
FAILED

Do not keep listening indefinitely.

Stop the SMS listener when:

- matching SUCCESS SMS is found
- matching FAILURE SMS is found
- 5-minute timeout occurs
- user cancels the verification flow
- payment is otherwise finalized

==================================================
PART 6 — DO NOT TREAT EVERY SMS AS A PAYMENT
==================================================

The phone may receive:

- OTP messages
- promotional SMS
- bank alerts
- UPI payment alerts
- other unrelated messages

Do NOT send every SMS to the backend as a payment.

At minimum, locally identify likely financial/transaction SMS using reasonable patterns/keywords.

Examples:

- debited
- credited
- paid
- payment
- UPI
- transaction
- txn
- Rs
- INR
- reference
- UTR

This is only preliminary filtering.

The BACKEND must perform the actual matching.

==================================================
PART 7 — SEND SMS TO SPRING BOOT
==================================================

When a relevant new SMS is detected, send it to the existing Spring Boot backend.

Use the authenticated Supabase JWT.

Example request concept:

POST /api/payments/{paymentId}/sms-verification

Authorization: Bearer <JWT>

Body:

{
  "smsBody": "...",
  "receivedAt": "...",
  "sender": "...",
  "packageName": "..."
}

Use the existing API naming conventions if the project already has a payment endpoint structure.

Do not expose database credentials or Supabase service keys in Flutter.

==================================================
PART 8 — BACKEND SMS VERIFICATION
==================================================

Spring Boot must compare the incoming SMS against the PENDING payment.

Use the original transaction information stored in the database.

Verify as much as possible from the SMS:

- amount
- merchant/UPI ID
- transaction/reference information
- debit/payment wording
- transaction status
- timing
- authenticated user/payment ownership

Do NOT blindly trust the Flutter app saying:

"payment successful"

The backend should determine the final status from the SMS information.

==================================================
PART 10 — SMS MATCHING
==================================================

Implement the SMS parser as a separate service/class.

Do not put all parsing logic inside the UI.

The parser should attempt to extract:

- debit/credit direction
- amount
- currency
- merchant/VPA if present
- UPI reference/UTR if present
- transaction status
- timestamp if present

Bank SMS formats vary.

Therefore make the parser modular and tolerant.

Do not assume one fixed bank SMS format.

If a field cannot be extracted, leave it null rather than inventing a value.

==================================================

==================================================

Prevent the same SMS from being processed multiple times.

Prevent the same payment from being finalized multiple times.

If the same SMS is delivered twice:

- do not create two payments
- do not create two successful transactions
- do not update the payment incorrectly

    Duration(minutes: 5);

Do not hardcode 5 minutes in multiple places.
